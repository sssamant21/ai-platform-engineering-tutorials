# Chapter 006 — AWS Workspace Provisioning

**Track:** Databricks SRE & Infrastructure Engineering  
**Part:** 02 — Cloud Provisioning and Networking  
**Audience:** AWS Infrastructure, SRE, Platform Engineering  
**Environment:** Disposable AWS staging account and Databricks account  
**Lab risk:** Provisioning incurs charges; do not apply to production without change approval

## 1. Objectives

By completing this chapter, you will:
1. Explain Databricks-on-AWS workspace provisioning models and the responsibility boundaries.
2. Identify required account access, cloud credentials, IAM roles, networking and storage.
3. Validate AWS prerequisites before Terraform applies changes.
4. Build a reproducible Terraform-based deployment plan using provider-supported resources.
5. Review IAM trust, cross-account access, workspace storage and network connectivity.
6. Diagnose provisioning failures, validate deployment and execute safe teardown.

## 2. Architecture and deployment choices

```text
  Platform operator / Terraform
               |
   Databricks account API / credentials
               |
       Databricks account
               |
       Workspace deployment
         /       |       \
   AWS IAM     VPC      Root storage
 cross-account routes    S3 bucket
       |         |          |
       +---------+----------+
                 |
          Classic compute
                 |
         S3 / data services

 Serverless compute uses a distinct Databricks-managed
 execution and connectivity model where supported.
```

For AWS, Databricks supports deployment models that differ in who provisions network and storage resources. **Customer-managed VPC** is an explicit architecture choice, not a universal prerequisite. Confirm supported options, region and features in the current AWS Databricks account deployment documentation.

A workspace's *root storage* is not interchangeable with Unity Catalog external locations or all workload data buckets. Separate responsibilities and access controls.

### Operational responsibilities

| Layer | SRE responsibilities |
|---|---|
| Databricks account | Account admin roles, workspace governance, credentials |
| AWS account | Identity, billing, limits, network ownership |
| Cross-account IAM | Least-privilege trust, role policy, audit |
| Workspace networking | Subnets, routes, DNS, egress, endpoints as required |
| Workspace root storage | S3 ownership, bucket policy, encryption, lifecycle |
| Classic compute | Instance capacity, runtime/policy, startup diagnosis |
| Serverless | Supported connectivity, access governance, usage/cost monitoring |
| Automation | Terraform state, change review, drift and rollback |

## 3. Deployment prerequisites

**Before starting:**
- An authorized Databricks account administrator or delegated provisioning principal.
- AWS IAM permissions to inspect and provision the resources chosen for the lab.
- A supported AWS region confirmed in Databricks documentation.
- AWS CLI, Terraform and Databricks CLI installed.
- A dedicated staging AWS account or approved isolated sandbox.
- Remote Terraform state with encryption, access controls and locking where supported.
- A cost budget, tags, owner and teardown window.

**Security rules:**
- Never commit AWS keys, Databricks OAuth secrets, PATs, Terraform state or generated plans containing secrets.
- Use AWS SSO/short-lived credentials and supported Databricks OAuth authentication.
- Do not use an administrator role for runtime workloads.
- Review the exact IAM trust and permissions generated by provider modules before deployment.
- Avoid exposing S3 buckets publicly.

## 4. Preflight lab — Verify AWS and tooling

PowerShell examples:

```powershell
aws --version
terraform version
databricks version

aws sts get-caller-identity
aws configure list
databricks auth profiles
```

Record the authorized AWS account ID in a private change record, not a public repository.

### Confirm region and capacity

```powershell
$env:AWS_REGION = "us-east-1"  # Example only; verify supported target region
aws ec2 describe-vpcs --region $env:AWS_REGION --query "Vpcs[].VpcId"
aws ec2 describe-subnets --region $env:AWS_REGION --query "Subnets[].{SubnetId:SubnetId,AZ:AvailabilityZone,VpcId:VpcId}" --output table
aws service-quotas list-service-quotas --service-code ec2 --region $env:AWS_REGION --max-results 20
```

**Note:** EC2 service quota results may be paginated; quota and actual capacity are different. A default VPC is not necessarily appropriate for Databricks. Validate supported subnet sizes, availability zones, route tables and security groups using the deployment documentation.

## 5. Choose a provisioning approach

Two common approaches:

**A. Databricks-managed networking/storage:** Use the supported account console and APIs to create a workspace with managed infrastructure where available. Document which resources Databricks provisions and which security requirements still belong to your team.

**B. Customer-managed VPC/storage:** Provision supported VPC, subnets, security groups, S3 root bucket and cross-account IAM role; register the required credentials, storage and network configuration in the Databricks account; then create the workspace.

This chapter's Terraform exercise uses **Approach B as an architecture lab**, but does not claim that one static configuration works for every region/account. Exact cross-account policies and trust relationships must come from current Databricks provider documentation or maintained reference modules.

```hcl
  alias = "accounts"
```

**Important:** This is intentionally a **safe scaffolding exercise**, not a complete deployable workspace module. Provisioning a functional workspace requires current, supported AWS IAM policies/trust, root storage and network configuration resources, Databricks account provider authentication, and a `databricks_mws_workspaces` (or currently supported equivalent) resource. ## 7. Deployment assembly checklist

For an approved customer-managed workspace deployment, use the maintained Databricks Terraform provider examples as the source of truth:

1. Create a VPC with suitable private subnets in supported availability zones.
2. Configure security groups, DNS, routing and required egress/endpoints.
3. Create a private, encrypted S3 root-storage bucket and approved bucket policy.
4. Create the Databricks cross-account role with the **documented** trust relationship and policies.
5. Register credentials, storage configuration and network configuration with Databricks account APIs.
6. Create the workspace using the returned configuration identifiers.
7. Wait for workspace readiness and test the authenticated workspace API.
8. Validate classic compute only in an approved staging environment.
9. Verify monitoring, audit, tags, cost attribution and teardown procedure.

Official references:
- https://registry.terraform.io/providers/databricks/databricks/latest/docs
- https://docs.databricks.com/aws/en/admin/workspace/
- https://docs.databricks.com/aws/en/dev-tools/terraform/

**Do not run `terraform apply` until the module is complete, reviewed and approved.**

## 8. Pre-apply security and operational review

Before any actual provisioning:


## 10. Failure injection tabletop

### Scenario A — Cross-account IAM trust mismatch

**Symptom:** workspace provisioning or compute access fails with a permissions or role-assumption error.

**Investigate:** trust principal, external ID/conditions where required, IAM policy scope, resource ARNs, account ID and recent IAM changes.

**Mitigation:** compare to the currently documented Databricks AWS trust/policy template and correct only through reviewed Terraform. Never temporarily grant `AdministratorAccess` to make the lab pass.

### Scenario B — Network connectivity failure

**Symptom:** workspace creation progresses but classic compute cannot communicate with required services.

**Investigate:** subnet routing, DNS resolution, security group egress, NAT/endpoints, NACLs, proxy rules and relevant logs.

**Mitigation:** restore documented required connectivity. Do not open all inbound ports or disable security controls.

### Scenario C — Insufficient EC2 capacity or quota

**Symptom:** cluster remains pending with a cloud provisioning error.

**Investigate:** regional quota, chosen instance family, AZ capacity, policy constraints and node type.

**Mitigation:** request quota or select an approved alternative instance type/zone. Distinguish quota limits from transient capacity shortage.

## 11. Troubleshooting matrix

| Symptom | Likely layer | First safe action |
|---|---|---|
| Databricks account API 401/403 | Account OAuth/role | Validate account-scoped profile and privileges |
| AWS AccessDenied | IAM policy/trust | Inspect CloudTrail and approved role definitions |
| Invalid network configuration | VPC/subnets/routes/SG | Compare network to current workspace requirements |
| S3 permission error | Bucket policy/role/KMS | Check exact principal, object path and key grants |
| Workspace created but cluster pending | EC2 quota/capacity/network | Inspect compute events and cloud logs |
| Terraform drift | Out-of-band change | Review plan before any reconciliation |
| Apply partially fails | Dependency or permissions | Preserve state and errors; avoid manual deletion |

## 12. Rollback and teardown runbook

A workspace deployment is a multi-resource operation; destroying resources without considering dependencies may break other workloads.

1. Stop new changes and preserve Terraform state and error evidence.
2. Identify resources created by the staging deployment and any shared dependencies.
3. Confirm no active jobs, retained data or downstream users depend on the workspace.
4. Back up required configuration and data per retention policy.
5. Use the provider-supported workspace deletion procedure and observe its retention behavior.
6. Execute `terraform plan -destroy` and review the full resource list.
7. Obtain approval; only then run `terraform destroy` for the isolated staging stack.
8. Verify cloud resources, S3 retention, IAM roles and billing for orphaned items.
9. Preserve sanitized audit evidence and close the change ticket.

**Never destroy a shared VPC, root bucket, KMS key or IAM role without proving it is exclusive to the disposable lab.** Terraform state loss or partial failures require reconciliation, not blind force-deletion.
